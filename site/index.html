A robot that checks its own moves.

Our camera-guided robot plays Connect-4 against a person. It refuses boards that cannot happen, picks its move with minimax, drops a real token, and only believes the move once its camera sees it.

Below, the robot's real code runs in your browser: the Python that reads the camera, checks the board, and plans, and the compiled Arduino sketch that drives the motors. Only the camera picture, motors, and table are simulated.

Two checks keep the game honest

  

    

      
Before it thinks

      
A new board from the camera only counts if it is exactly one legal move away from the last board the robot trusted. A chip that vanished, two new chips at once, or a chip floating above an empty cell: the robot rejects it and keeps the last good board.

    

    

      
After it moves

      
When the robot drops a token, it already knows what the board should look like. It accepts its own move only when the camera shows that exact board within 10 seconds. A token that slid into the wrong column stops the robot with an error, instead of silently corrupting the game.

    

  

  





  
  

  
The robot

  
    
    
  • Raspberry Pi 4 reads the camera, runs the validator and minimax, and serves the dashboard.
    • 
    
  • Arduino Uno moves the carriage to the column, then releases one token with an encoder-counted magazine.
    • 
    
  • 6,100 EGP in parts for the final build, about 115 USD at the April 2026 rate. An earlier design with stepper motors and a servo gate was priced at 10,135 EGP.

Time per move

      
3 to 15 s from command to a verified move, 7.5 s on average. Most of it is the mechanism and the camera check, not the image processing.

    

  

  

    
Limits

    
    
    
  • All results come from one fixed camera mount and steady indoor light. Glare and other lighting shift the colour thresholds.
    • 
    
  • The carriage has no position sensor, so the far columns miss more often.
    • 
    
  • Board detection assumes the camera sees only the grid. Our demo photo shows the board on its blue legs, which the robot's camera never saw: the legs join the blue frame, so automatic detection reads 32 of 42 holes right. With the grid's own corners, the same code reads all 42.
    • 
    
  • We did not keep the labelled images and drop logs behind the numbers above, so they cannot be re-run.
    • 
    
  • The dashboard has no login: anyone on the same network can send moves.
    • 
  

  






  
How it works

  
How the robot reads the board, what it does after each move, and where each part lives in the code.

  

    
    

      
How it reads the board

      
    
        
  1. Find the blue board frame by colour, and smooth its four corners over frames.
    2. 
        
  2. Warp the board to an 800 by 800 top-down view.
    3. 
        
  3. Brighten it (+20), stretch the contrast (×1.3), and blur it (5 by 5 Gaussian).
    4. 
        
  4. Cut the view into a 6 by 7 grid and read the centre of each cell as empty, red, or yellow.
    5. 
      

    

  

  

    
After each robot move

    
  

  

    
Where it lives in the code

    
    
    
  • vision.py finds the blue frame, warps it to 800 by 800, and reads each hole with HSV colour rules.
    • 
    
  • game_state.py is gate 1, the validator that accepts only one legal move.
    • 
    
  • minimax.py searches 5 moves ahead with alpha-beta pruning.
    • 
    
  • hardware.py sends the column over serial and runs gate 2, the camera check.
    • 
    
  • dispenser.ino drives the carriage by timing, then releases one token by encoder count. We rebuilt it from the final report, because the file that ran in the demo was not kept.
